## Production defect found and fixed

The first M7D4 production canary reached a healthy private `details_pending` stage but failed before any affected-detail message was queued.

Read-only retained-fixture diagnosis proved:

- stage safety outcome `proceed`;
- one staged observation;
- one `CHANGED` event with `needs_detail=1`;
- `expected_detail_count=1`;
- `detail_enqueue_cursor=0`;
- `queued_detail_count=0`;
- zero candidate detail/media rows.

The root cause was the tenant data-plane dispatch identity boundary. The first post-stage fan-out query was intentionally run-scoped and therefore did not contain a tenant-shaped SQL parameter. The shared `TENANT_DISPATCH` routing adapter previously inferred tenant identity only from batch parameters, so it failed closed with `tenant_data_plane_tenant_unresolved`; the scan wrapper surfaced the bounded higher-level code `tenant_import_scan_failed`.

The production fix allows the shared data-plane query path to receive the exact tenant identity only from already server-resolved trusted context. Any conflict between that explicit tenant and tenant identities found in SQL parameters fails closed before dispatch. M7D4 fan-out and candidate writes carry that trusted identity. No direct D1 REST fallback was introduced.
