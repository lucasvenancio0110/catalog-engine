### M6D2 — Knowledge-Pack-driven merchandising

PR `#87` introduced:

- `CEI_MERCHANDISING_CONTRACT_VERSION=1`;
- Knowledge Pack owned merchandising/navigation definitions;
- Sports navigation moved into Sports Pack v1;
- tenant merchandising persistence;
- public-safe `catalog_meta.navigation`;
- versioned internal `catalog_meta.merchandising`;
- verification for navigation/merchandising integrity;
- a fake non-Sports Wheels pack fixture proving the merchandising Core is domain-neutral.

The first production canary failed at verification. PR `#88` improved safe canary diagnostics without weakening verification. The next canary identified the exact finding:

`merchandising_metadata_invalid`.

Root cause was D1/SQLite type coercion: the tenant D1 boundary stringified parameters, while verification compared JSON-extracted INTEGER contract version against TEXT `"1"` in an expression without useful column affinity.

PR `#89` fixed the verification expression with explicit INTEGER coercion and added a real SQLite regression test.

## Known non-blocking debt after M6

M6 closure does not claim the entire product is launch-ready.

Open debt includes:

- M1 branch protection / required-check governance;
- third-party Actions/toolchain governance; GitHub currently warns that some action versions target deprecated Node 20 internals and are being forced onto Node 24;
- production migration parity/runbook hardening;
- backup/rollback/recovery documentation;
- M7 catastrophic sync-diff protection and last-known-good behavior;
- M8 media trust-boundary hardening;
- later storefront/portal/auth/billing/onboarding milestones.

These are roadmap work, not reasons to keep M6 open.

## Next milestone

M7 — **Intelligent Sync v2** is now the active roadmap milestone.

M7 must make recurring synchronization safe enough that supplier outages, partial scans, malformed scans or implausible volume drops cannot silently destroy a healthy published catalog.
