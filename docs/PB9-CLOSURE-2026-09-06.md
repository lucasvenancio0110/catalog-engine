## Root causes resolved during PB9

PB9 exposed several independent blockers; each was fixed at the narrowest proven boundary rather than bypassing tenant/runtime safety.

### Runtime starvation

An older incomplete tenant runtime job could occupy bounded scheduler selection ahead of a fully eligible merchant. Discovery/due selection was tightened so incomplete historical state cannot starve a ready runtime candidate.

### Administrative Cloudflare call from inside the application Worker

After CROCCODILOS reached runtime processing, the application Worker recorded `cloudflare_platform_unreachable` while attempting to upload/update a tenant Worker through the Cloudflare administrative API.

The authority boundary was corrected:

```text
application cron
-> discovers/durably queues eligible runtime work

trusted GitHub CI
-> seeds bounded public runtime metadata
-> uploads the full Workers-for-Platforms tenant runtime
-> marks the runtime staged

application Worker + TENANT_DISPATCH
-> smoke-tests the exact staged tenant runtime
-> promotes staged -> verified only after successful isolated health/catalog proof
```

The application Worker no longer owns the administrative tenant-Worker upload.

### Shared production-concurrency collision

Application deploy and trusted tenant provisioning/runtime staging were both triggered by the same push and shared `catalog-engine-production-d1`. GitHub concurrency can retain only one pending run for a group, causing a sibling run to be cancelled before execution.

The trusted provisioning/runtime-staging workflow no longer triggers on push. It remains bounded on its five-minute schedule and explicit trusted-main dispatch, while actual production mutations remain serialized with `cancel-in-progress: false`.

### Misleading merchant-card loading state

The portal initially rendered a disabled generic `Abrir loja` action before the real store status request completed, then replaced it with `Ver andamento`. PB9 removed that flicker; unresolved status now renders a neutral loading state until durable merchant state is known.

## Security and privacy boundary preserved

PB9 retains all campaign invariants:

- tenant authority is resolved server-side from authenticated membership;
- browser input never supplies Worker/D1/runtime routing authority;
- preview session capability remains short-lived, host-only, `HttpOnly`, `Secure` and `SameSite=Strict`;
- only the SHA-256 capability hash and bounded ownership/expiry state are persisted server-side;
- preview catalog/media access is read-only;
- preview is private/no-store/non-indexable and no-referrer;
- supplier URLs, raw provider IDs, D1 identifiers, Worker locators, Cloudflare identifiers, private CEI evidence, secrets and tokens are not exposed;
- no default-tenant fallback exists for merchant preview;
- preview readiness remains separate from public custom-domain publication.
