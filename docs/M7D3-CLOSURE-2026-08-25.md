## Bounded outcome

M7D3 connects an enrolled incremental job to the real provider scan path, applies the existing safety and provider-neutral listing-delta contracts, writes the resulting observation/event/taxonomy state into the tenant-private stage, and stops at `details_pending` when affected detail is required.

M7D3 does **not** fetch affected detail, run affected-only CEI, verify a complete candidate, promote canonical state, advance a sync cursor, apply repeated-miss removal, or enable recurring Intelligent Sync.

## Final production code

Final production-proven application SHA:

`75060957930a451c37dace8ad883bcfbe042485c`

Final hotfix PR:

`#136 — M7D3 hotfix: fix D1 stage count parameter affinity`

The production-only defect was caused by the Cloudflare D1 wrapper normalizing non-null bound parameters to strings. The strict stage seal compared SQLite integer `COUNT(*)` directly with the expected taxonomy-count parameter. Observations/events compared persisted integer columns and therefore passed while the taxonomy comparison failed. The fix keeps the seal fail-closed and explicitly casts the bound expected taxonomy count with `CAST(?6 AS INTEGER)`.

A regression now reproduces the real Cloudflare binding behavior by stringifying seal parameters before SQLite execution.
